# Спецификация: «Покер планирования» (Planning Poker)

Версия: 1.0
Статус: рабочая (соответствует коммиту `22a7c9c`)
Назначение: документ для развёртывания приложения внутри организации и для оценки миграции с Supabase на self-hosted.

---

## 1. Назначение и цели

Веб-приложение для командной оценки задач методом Planning Poker (покер планирования).

Цели:
- Ведущий создаёт комнату и запускает раунд голосования.
- Участники голосуют картами, не видя чужих значений до вскрытия.
- После вскрытия все видят карты и итоговую оценку (консенсус или медиана).
- Состояние хранится на сервере и переживает отключение любого участника, включая ведущего.

Что НЕ входит в scope:
- Аутентификация/SSO (сейчас — анонимный вход по имени).
- История раундов, экспорт, интеграции с трекерами (Jira и т.п.).
- Администрирование и модерация.
- Аудит и разграничение прав (см. раздел «Безопасность»).

## 2. Архитектура (as-is)

```
Браузер (статический SPA, без сборки)
  index.html
  styles.css
  app.js            — вся логика (ES-модуль)
  supabase-config.js — URL + publishable key (ES-модуль)
  supabase.js       — вендоренный supabase-js (UMD, 218 КБ, без CDN)

        │  HTTPS REST (PostgREST)
        │  WSS Realtime (postgres_changes)
        ▼
Supabase (managed)
  PostgreSQL
    public.rooms
    public.participants
    public.votes
    RPC public.leave_room(room_id, uid)
  Realtime (publication supabase_realtime)
  PostgREST (REST API поверх таблиц/RPC)
```

Ключевые свойства:
- Нет собственного backend-кода: клиент ходит напрямую в PostgREST/Realtime.
- Нет шага сборки: файлы отдаются как есть.
- Все внешние ресурсы локальные (никаких CDN) — приложение работает в закрытом контуре.

## 3. Роли

| Роль | Как получается | Права |
|---|---|---|
| Ведущий (host) | Первый вошедший в пустую комнату; либо выбравший роль «Ведущий», если в комнате ещё нет ведущего | Старт раунда, вскрытие, сброс, таймер. Не голосует, наблюдает |
| Участник (participant) | Все остальные | Голосование картой, отмена голоса, выход |

Особенности:
- Ведущий присутствует в таблице `participants`, но исключается из рассадки и «кота» карт.
- Ведущий один на комнату.
- Ограничение: если ведущий вышел, а участники остались, комната продолжает жить без ведущего (сменить роль в UI нельзя). См. «Ограничения».

## 4. Пользовательские сценарии

### 4.1 Создание комнаты
1. Ввести имя, выбрать роль (по умолчанию «Участник»).
2. «Создать комнату» → генерируется код из 6 символов.
3. Создаётся запись в `rooms` (status=`idle`), пользователь входит в неё.
4. Так как комната пуста, создатель становится ведущим.
5. Ссылка вида `https://host/#ABC123` копируется кнопкой «Скопировать ссылку».

### 4.2 Вход по коду/ссылке
1. Код из `#hash` автоматически подставляется в поле.
2. Ввести имя → «Войти».
3. Если комната не найдена — сообщение «Комната с таким кодом не найдена».
4. Участник добавляется в `participants` (upsert по `room_id,uid`).

### 4.3 Раунд
1. Ведущий нажимает «Начать раунд» → `rooms.status = voting`, голоса очищаются.
2. Участники видят карты: `? 0.5 1 2 3 5 8 13 ☕`. Клик по карте пишет голос в `votes` (upsert по `room_id,uid`); повторный клик по той же карте отменяет голос.
3. Своя карта видна участнику сразу (значение), чужие — «рубашкой» с галочкой факта голоса.
4. Ведущий видит счётчик «Проголосовали: X из Y».
5. «Вскрыть карты» → `rooms.status = done`, в `rooms.result` сохраняется снимок `{summary, votes:[...]}`.
6. Все карты переворачиваются с анимацией, показывается итог: «консенсус» либо «медиана», отдельно — пропуски (☕).
7. «Сбросить» → `rooms.status = idle`, голоса удаляются, стол очищается.

### 4.4 Таймер (опционально)
1. Ведущий выбирает 1/2/3/5/10 минут или «Стоп».
2. Таймер хранится в `rooms.timer = {duration, startAt, endAt}` (epoch ms).
3. Клиенты тикают локально каждые 250 мс; по старту и по окончании — звуковой сигнал (WebAudio).
4. По истечении ведущий автоматически очищает таймер (`timer = null`).

### 4.5 Выход
- «Покинуть комнату» или закрытие вкладки → RPC `leave_room(room_id, uid)`.
- Если участников не осталось — комната и её голоса удаляются каскадом.
- Ссылка очищается (`history.replaceState`), страница перезагружается.

## 5. Функциональные требования

- FR-1: создание комнаты с уникальным 6-символьным кодом.
- FR-2: вход в комнату по коду; при неверном коде — понятная ошибка.
- FR-3: роли host/participant; первый в пустой комнате — host.
- FR-4: список участников и счётчик онлайна (по факту присутствия в комнате).
- FR-5: старт раунда, очистка голосов, смена статуса.
- FR-6: голосование картами; смена и отмена голоса.
- FR-7: скрытие чужих голосов до вскрытия.
- FR-8: вскрытие с расчётом итога (консенсус/медиана/пропуски).
- FR-9: сброс раунда.
- FR-10: таймер с настройкой длительности и уведомлением.
- FR-11: синхронизация состояния между клиентами в реальном времени.
- FR-12: устойчивость к отключению любого клиента (состояние на сервере).
- FR-13: работа в закрытом контуре без внешних CDN.
- FR-14: мобильная и десктопная вёрстка.

## 6. Модель данных

### 6.1 `public.rooms`
| Поле | Тип | Ограничения | Описание |
|---|---|---|---|
| `id` | text | PK | Код комнаты (6 символов) |
| `status` | text | not null, default `'idle'` | `idle` \| `voting` \| `done` |
| `timer` | jsonb | null | `{duration, startAt, endAt}` (ms epoch) |
| `result` | jsonb | null | `{summary, votes:[{uid,name,value}]}` |
| `created_at` | bigint | not null | ms epoch |

### 6.2 `public.participants`
| Поле | Тип | Ограничения | Описание |
|---|---|---|---|
| `room_id` | text | not null, FK → rooms.id ON DELETE CASCADE | Комната |
| `uid` | text | not null | Идентификатор пользователя (localStorage UUID) |
| `name` | text | not null | Имя |
| `role` | text | not null, default `'participant'` | `host` \| `participant` |
| `joined_at` | bigint | not null | ms epoch |

PK: `(room_id, uid)`.

### 6.3 `public.votes`
| Поле | Тип | Ограничения | Описание |
|---|---|---|---|
| `room_id` | text | not null, FK → rooms.id ON DELETE CASCADE | Комната |
| `uid` | text | not null | Пользователь |
| `name` | text | not null | Имя (денормализовано для снимка) |
| `value` | text | not null | `?`, `0.5`, `1`, `2`, `3`, `5`, `8`, `13`, `☕` |

PK: `(room_id, uid)`.

### 6.4 Realtime и RPC
- `alter table ... replica identity full` для всех трёх таблиц.
- Публикация `supabase_realtime` включает `rooms`, `participants`, `votes`.
- RPC `public.leave_room(room_id text, uid text)`:
  1. удаляет участника;
  2. если участников в комнате не осталось — удаляет комнату (голоса удаляются каскадом).

### 6.5 Индексы
- PK покрывают все запросы (`rooms.id`, `(room_id,uid)`).
- Дополнительные индексы не требуются при текущих объёмах.

## 7. Серверный контракт (что именно вызывает клиент)

Заголовки для всех REST-запросов:
```
apikey: <publishable key>
Authorization: Bearer <publishable key>
Content-Type: application/json
```

| Операция | Метод и путь | Примечание |
|---|---|---|
| Проверка комнаты | `GET /rest/v1/rooms?select=id&id=eq.{code}` | ответ пустой → «не найдена» |
| Создание комнаты | `POST /rest/v1/rooms?on_conflict=id` + `Prefer: resolution=ignore-duplicates` | upsert |
| Список ролей | `GET /rest/v1/participants?select=uid,role&room_id=eq.{code}` | определение ведущего |
| Вход в комнату | `POST /rest/v1/participants?on_conflict=room_id,uid` | upsert |
| Синк участников | `GET /rest/v1/participants?select=uid,name,role&room_id=eq.{code}` | каждые 5 с + realtime |
| Синк голосов | `GET /rest/v1/votes?select=uid,name,value&room_id=eq.{code}` | каждые 5 с + realtime |
| Синк комнаты | `GET /rest/v1/rooms?select=id,status,timer,result&id=eq.{code}` | каждые 5 с + realtime |
| Голос | `POST /rest/v1/votes?on_conflict=room_id,uid` | upsert |
| Отмена голоса | `DELETE /rest/v1/votes?room_id=eq.{code}&uid=eq.{uid}` | |
| Старт раунда | `DELETE /rest/v1/votes?room_id=eq.{code}` + `PATCH /rest/v1/rooms?id=eq.{code}` (`status=voting`) | две операции |
| Вскрытие | `PATCH /rest/v1/rooms?id=eq.{code}` (`status=done`, `result=...`) | |
| Сброс | `DELETE /rest/v1/votes?room_id=eq.{code}` + `PATCH /rest/v1/rooms?id=eq.{code}` (`status=idle`) | |
| Таймер | `PATCH /rest/v1/rooms?id=eq.{code}` (`timer=...`) | |
| Выход | `POST /rest/v1/rpc/leave_room` body `{room_id, uid}` | `keepalive` при закрытии вкладки |

Realtime:
- Канал: `room:{code}`.
- Подписки `postgres_changes`:
  - `table=rooms, filter=id=eq.{code}`
  - `table=votes, filter=room_id=eq.{code}`
  - `table=participants, filter=room_id=eq.{code}`
- На любое событие — перечитывание соответствующей таблицы и перерисовка.
- Резервный механизм: опрос всех трёх таблиц каждые 5 секунд (если realtime не доставил событие).
- `eventsPerSecond: 10` на клиенте.

Важно для реализации на другом backend: клиент **не полагается на payload realtime-события** — он только получает сигнал и перечитывает состояние через GET. Это упрощает замену realtime на любой «пинг» (WebSocket/SSE/SSE-заглушка/долгий polling).

Структура `app.js` (функциональные блоки):
- утилиты: `esc`, `makeCode`, `deleteAll`;
- вход: `requireName`, `createRoom`, `joinByCode`, `enterRoom`;
- синхронизация: `setupSync`, `syncParts`, `syncVotes`, `syncRoom`, `safeRender`;
- выход: `leaveRoomSilent`, `leaveRoom`, `teardown`;
- рендер: `render`, `renderParticipants`, `renderRoundHead`, `renderTable`, `renderSeats`, `seatHtml`, `renderPot`, `renderVoteArea`;
- операции: `startRound`, `castVote`, `cancelVote`, `revealRound`, `resetRound`, `computeSummary`;
- таймер: `setTimer`, `stopTimer`, `tick`, `renderTimer`, `positionTimerRow`, `chime`;
- инициализация: `initFromHash`, привязка кнопок.

Локальное состояние (в памяти вкладки):
- `uid` — UUID из `localStorage['pp_uid']` (создаётся при первом входе);
- `participants{uid:{name,role}}`, `votes{uid:{name,value}}`, `room{status,timer,result}`;
- `flipped{}`, `placed{}` — флаги для анимаций;
- `channel` — realtime-канал, `syncTimer` — интервал опроса.

Расчёт итога (`computeSummary`):
- `☕` — пропуск (в расчёт не входит, считается отдельно);
- `?` — трактуется как бесконечность;
- числа — числовое сравнение;
- все равны → «X (консенсус)», иначе медиана.

## 9. Конфигурация

`supabase-config.js`:
```js
export const SUPABASE_CONFIG = {
  url: "https://<project-ref>.supabase.co",
  anonKey: "<publishable key>"
};
```
- Оба значения **публичные** (ключ publishable/anon не является секретом).
- Секретный `service_role`/secret key в клиент **не попадает**.
- Для другой платформы аналог конфигурации: `API_BASE_URL` + `WS_URL` (или относительные пути при том же origin).

## 10. Развёртывание

### 10.1 Как есть (GitHub Pages)
- Workflow `.github/workflows/deploy.yml`: на push в `main` выкладывает содержимое репозитория как статику.
- Требования: включённый Pages с источником «GitHub Actions».

### 10.2 Внутри организации (статический хостинг)
Любой веб-сервер, отдающий статику. Пример nginx:
```nginx
server {
  listen 443 ssl;
  server_name poker.example.internal;
  root /var/www/poker;
  index index.html;

  add_header Content-Security-Policy "default-src 'none'; base-uri 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self' https://<project-ref>.supabase.co wss://<project-ref>.supabase.co; font-src 'self'; object-src 'none'; frame-ancestors 'none'" always;
  add_header X-Content-Type-Options nosniff always;
  add_header Referrer-Policy no-referrer always;
}
```
Обязательно:
- TLS (HTTPS) — нужен для `crypto.randomUUID`, `navigator.clipboard`, WebSocket.
- `connect-src` должен включать домен API и WSS.
- Никаких CDN не требуется — все ассеты локальные.

### 10.3 Self-hosted Supabase (если остаёмся на текущем стеке)
Docker Compose из официального репозитория Supabase; приложение не меняется, меняется только `url`/`anonKey` (и JWT-секрет). Нужны: Postgres, PostgREST, Realtime, (опционально) Studio/Auth. Далее — TLS-прокси и бэкапы.

## 11. Безопасность

Текущая модель (как в старом Firebase-варианте):
- RLS **выключен**, publishable-ключ публичный.
- Любой, кто знает URL и ключ, может читать/писать таблицы.
- Код комнаты — единственный «секрет» (6 символов, перебор возможен).
- Нет аутентификации: имя вводится вручную, `uid` генерируется на клиенте.

Риски: порча данных, подслушивание голосов, удаление чужих комнат.

Рекомендации для внутреннего развёртывания:
1. Включить RLS и политики (чтение — участникам комнаты; запись голоса — только своему `uid`).
2. Ввести аутентификацию (корпоративный SSO/OIDC) и привязать `uid` к пользователю.
3. Ограничить доступ на уровне сети (VPN/внутренний контур) и WAF.
4. Логировать доступ; делать бэкапы БД.
5. Ограничить частоту запросов (rate limiting) на прокси.

## 12. Нефункциональные требования

- Браузеры: актуальные Chrome/Edge/Safari/Firefox (ES-модули, `crypto.randomUUID`, WebSocket, WebAudio).
- Мобильные: адаптивная вёрстка, `viewport-fit=cover`.
- Задержка: обновление состояния — доли секунды при работающем realtime; гарантированно ≤ 5 с (резервный опрос).
- Масштаб: проверено 16 пользователей в комнате (1 ведущий + 15 участников), 15 карт на столе, вскрытие 15/15.
- Устойчивость: состояние на сервере; отключение ведущего не останавливает голосование.
- Нет внешних зависимостей времени выполнения (кроме API Supabase).
- Хранение: данные комнат эфемерны; после выхода последнего участника комната удаляется.

## 13. Тестирование и приёмка

Функциональные проверки:
1. Создание комнаты → код 6 символов → создатель ведущий.
2. Вход второго участника → появляется в списке и за столом.
3. Старт раунда → статус «Голосование», голоса пусты.
4. Голос участника → карта на столе; смена голоса; отмена.
5. Чужие голоса скрыты до вскрытия.
6. Вскрытие → все карты перевёрнуты, итог = консенсус/медиана.
7. Сброс → стол пуст, статус «Ожидает».
8. Таймер 1 мин → отсчёт у всех, сигналы старта/окончания.
9. Выход участника → исчезает; выход последнего → комната удалена.
10. Закрытие вкладки ведущего → участники продолжают видеть состояние; вскрытие доступно после повторного входа ведущего.
11. Ссылка с `#кодом` → код подставлен автоматически.
12. Max-тест: 16 пользователей, 15 карт, вскрытие.
13. Работа под строгим CSP (`script-src 'self'`, без `unsafe-inline`/`unsafe-eval`).
14. Мобильный вид (портрет/ландшафт).

Регрессия, которую важно не потерять:
- Все записи в БД должны быть `await`-нуты (postgrest-js ленивый: без `await`/`.then()` запрос не отправляется). Это был реальный баг (исправлен в `22a7c9c`).

## 14. Ограничения и известные проблемы

- Нет истории раундов и экспорта.
- Нет смены роли после входа; если ведущий вышел, а участники остались — ведущего нет.
- Нет защиты от подмены имени/`uid` (клиентский UUID).
- RLS выключен (см. «Безопасность»).
- Комната удаляется, когда её покидает последний участник.
- Код комнаты 6 символов — возможен перебор.
- Realtime-события используются только как сигнал; при их потере состояние догоняется опросом раз в 5 с.
- Ошибка в консоли вида `reportAllChanges ... startTime` — от Chrome-расширения (web-vitals), к приложению отношения не имеет.

## 15. Уход от Supabase / self-hosted варианты

Да, приложение можно развернуть без Supabase. Архитектурно оно очень простое: 3 таблицы, REST CRUD и «пинг» об изменениях. Ниже варианты.

### Вариант A. Self-hosted Supabase (минимум изменений) — рекомендуется
- Развернуть официальный Supabase (Docker Compose): PostgreSQL + PostgREST + Realtime (+ Studio/Auth).
- **Клиент не меняется**: тот же `supabase-js`, только `url`/`anonKey` указывают на ваш инстанс.
- Что сделать: TLS-прокси, бэкапы Postgres, мониторинг, при желании — Auth/SSO и RLS.
- Плюсы: нулевая переработка кода; знакомая модель.
- Минусы: несколько контейнеров в эксплуатации; Realtime-сервис требует ресурсов.

### Вариант B. Собственный лёгкий backend (Node.js + PostgreSQL + WebSocket)
- Реализовать REST-эндпоинты, эквивалентные таблице из раздела 7, и WS/SSE-уведомления.
- Переписать в `app.js` только слой данных: функции `createRoom`, `joinByCode`, `enterRoom`, `setupSync`, `syncParts/Votes/Room`, `startRound`, `castVote`, `cancelVote`, `revealRound`, `resetRound`, `setTimer`, `stopTimer`, `leaveRoomSilent`.
- Рендер и вся UI-логика остаются без изменений.
- Плюсы: полный контроль, SSO/аудит/RLS на уровне API, один сервис, легко в закрытом контуре.
- Минусы: нужно писать и сопровождать backend; объём — ~1–2 дня на этот функционал (без SSO).

### Вариант C. PocketBase (один бинарник + SQLite)
- Готовые REST, realtime (SSE), админка и auth.
- Переписать слой данных под API PocketBase (коллекции `rooms`, `participants`, `votes`).
- Плюсы: минимальная эксплуатация, один файл, встроенная админка.
- Минусы: SQLite (нет горизонтального масштабирования), другая модель API, ограничения realtime-фильтров.

### Вариант D. Go/Java + PostgreSQL + WebSocket
- Аналог B, но на «корпоративном» стеке.
- Плюсы: соответствие стандартам организации, производительность.
- Минусы: больше кода/времени, чем B.

### Вариант E. Firebase (предыдущая версия)
- Не on-prem: данные в Google Cloud. Для внутреннего контура обычно не подходит.

### Сравнение

| Критерий | A: Self-hosted Supabase | B: Node+PG+WS | C: PocketBase | D: Go/Java+PG+WS |
|---|---|---|---|---|
| Изменения клиента | нет | средние (слой данных) | средние | средние |
| Эксплуатация | 4–6 контейнеров | 1 сервис + БД | 1 бинарник | 1 сервис + БД |
| SSO/аудит | через Auth/прокси | полностью контролируемо | встроенный auth | полностью контролируемо |
| Масштабирование | горизонтальное | горизонтальное | ограничено (SQLite) | горизонтальное |
| Срок внедрения | 0.5–1 день | 1–3 дня | 1–2 дня | 3–5 дней |
| On-prem/air-gap | да | да | да | да |

### Миграция данных
Данные эфемерны (комнаты живут до выхода последнего участника), поэтому переносить обычно нечего. При необходимости: выгрузить `rooms/participants/votes` в JSON/CSV через PostgREST и импортировать в новую БД.

### Рекомендация
- Нужно «поднять у себя» с минимумом работ → **Вариант A (self-hosted Supabase)**.
- Нужен один собственный сервис, SSO и контроль → **Вариант B**.
- Нужен максимально простой деплой на небольшой отдел → **Вариант C**.
